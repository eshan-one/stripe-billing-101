Stripe Subscriptions, Explained

A software team wanted customers to pay every month. Before anyone built it, one engineer learned how the payment side works by trying it in a practice account. Each section below explains what happened in plain language, then shows the technical detail underneath.

The short version

Practise first

Everything was tried in a practice account with play money. No real software had been written yet.

Watch the messages

Stripe sends a stream of small notes such as "payment received". Reading them first showed what the app has to handle.

Break it on purpose

Declined cards, empty accounts and extra bank checks were tested deliberately, because that is where things go wrong.

Write down what you don't know

The engineer kept a short list of open questions, each with a sensible default, for the people who own the product.

What problem is being solved

Imagine a software product that costs $8 a month. Someone has to collect the card details, charge the card every month, send receipts, retry when a payment fails, and tell the software to switch the plan on or off.

Stripe is a company that does that work. The team's app still has to be connected to Stripe, and that connection was the engineer's job.

Customer

The person who wants the plan and pays for it.

The app

The team's software. It decides who gets which plan.

Stripe

Holds the card, takes the money, sends receipts and reports back.

Technical detail

Setup: sandbox and the Stripe CLI

Everything ran in a Stripe sandbox, so no real money moves. Two terminal tabs: one for commands, one for the event stream.

brew install stripe/stripe-cli/stripe
stripe login
stripe products list --limit 3

The CLI makes the same API calls the backend will make, so the raw requests and responses are visible before any app code exists.

Payments, billing and subscriptions

These three words sound alike, and sorting them out was the first useful hour. The page the engineer opened first was about one-time payments, which is not what a subscription needs.

Payments

Moving money once.

"Take $100 now"

Billing

Charging again and again, with invoices and retries.

"Charge $100 every month"

Subscription

One customer's ongoing plan.

"Acme is on the Pro plan, monthly"

A product is what you sell, like a menu item. A price is the tag on it. They are kept separate so a price can change without rewriting the menu.

Technical detail

Billing sits on top of Payments: a subscription creates an invoice each period, and Stripe collects it through the Payments machinery. For this task, plans were Billing and credit packs were Payments. Subscriptions live under Revenue, then Billing in Stripe's docs.

One purchase, step by step

This is what happens between a customer clicking Subscribe and the plan switching on.

  1. Customer
    Clicks Subscribe
  2. The app
    Asks Stripe for a payment page
    It also attaches a note saying which customer organisation this is, so the answer can be matched up later.
  3. Stripe
    Opens an unpaid order form
    This form is not the subscription yet. Nothing exists until someone pays.
  4. Customer
    Enters their card on Stripe's page
  5. Stripe
    Charges the card and creates the records
    A customer record, a subscription and the first invoice.
  6. Stripe
    Sends the app a handful of messages
    These messages are called webhooks.
  7. The app
    Checks the message is genuine and switches the plan on
    It never trusts the customer's browser for this. Only the messages count.

Creating the Checkout Session with the CLI

stripe checkout sessions create \
  -d mode=subscription \
  -d success_url=https://example.com/success \
  -d "line_items[0][price]=<PRICE_ID>" \
  -d "line_items[0][quantity]=1"

The same request with curl, as the backend would send it

curl https://api.stripe.com/v1/checkout/sessions \
  -u "$STRIPE_SECRET_KEY:" \
  -d mode=subscription \
  -d success_url=https://example.com/success \
  -d "line_items[0][price]=<PRICE_ID>" \
  -d "line_items[0][quantity]=1" \
  -d "managed_payments[enabled]=false"

An error nobody expected

The account had Managed Payments on by default and the test product had no tax code, so the first call failed:

{
  "error": {
    "message": "Invalid line_items[0]: the product tax code is missing ... Product tax code is required for Managed Payments, which is enabled by default on your account. If you want to disable Managed Payments on this session, you can pass managed_payments[enabled]=false ...",
    "type": "invalid_request_error"
  }
}

The fix was the one extra parameter -d "managed_payments[enabled]=false", which changes nothing account-wide. The account setting itself was left alone and raised as a question.

What the Checkout Session response contains

It is an open order form, not the subscription.

What gets created

  • Customer record
  • Subscription
  • Invoice

Everything is created, but only after the payment succeeds.

The finding that mattered most: a failed first payment leaves nothing behind. No customer record, no subscription, no invoice. The software has nothing to clean up, and the customer can simply try again. Failed payments in later months are a different case, and have not been tested yet.

Four surprises

One purchase sends twelve kinds of message

Each kind arrived twice. The app only needs about three of them: the subscription was created, the invoice was paid, and checkout finished.

Messages arrive in no fixed order

"Invoice paid" showed up before "customer created". Any plan that assumes an order will break, so the app has to read what each message says.

The payment page is not the subscription

It is an open order form. The subscription only exists once the customer has paid, which is why the app waits for Stripe's message instead of trusting the browser.

One default setting was a business decision

An account setting about who counts as the legal seller blocked the first test. The engineer worked around it for that single test and wrote it down as a question instead of changing it, because it affects tax and accounting.

Technical detail

The event firehose

One successful checkout produced 12 distinct events, each delivered twice: once as name and once as v1.name. The v1. copies look like the same events in Stripe's newer format. That is inferred and not confirmed, so they were ignored. Arrival order is not logical order: invoice.paid arrived before customer.created, and checkout.session.completed arrived before invoice.created.

What the engineer would actually build

After a few hours the picture was clear enough to draw. Only three pieces are code the engineer has to write: a small request that asks Stripe for the payment page, a listener that receives Stripe's messages, and the bookkeeping that records the result. Everything else is screens or runs on Stripe's side.

Six design rules that came out of the experiments

  1. Webhooks are the source of truth, not the redirect to success_url. The browser can close, lie or be slow.
  2. Don't rely on event order. Read the payload.
  3. Deduplicate on the evt_ ID. Events can repeat.
  4. Verify the signature with the whsec_ secret.
  5. A webhook has no login and no user. Put your own user or org ID on the Stripe objects (metadata or client_reference_id) when creating the session, or the webhook cannot say whose payment it is.
  6. Wait for invoice.paid, not just checkout.session.completed, before granting access.

A method you can borrow for any new tool

Nothing here is specific to payments. These nine steps work for learning any unfamiliar system before you commit to building on it.

  1. Learn the vocabulary before the instructions.
  2. Practise in a safe copy of the real thing.
  3. Do it by hand before automating anything.
  4. Watch the messages the system produces.
  5. Do one successful run and read what it created.
  6. Learn which messages matter and ignore the rest.
  7. Break it on purpose and note what is not created.
  8. Draw who does what.
  9. Write down what you don't know, each with a default.

Words used on this page

Sandbox
A practice copy of Stripe where nothing is real and no money moves.
Subscription
A customer's ongoing plan that is charged on a schedule.
Invoice
The bill created for each billing period.
Webhook
A message Stripe sends to the app when something happens, such as a payment succeeding.
Event
One of those messages. Each has a name such as invoice.paid and an ID starting with evt_.
Checkout
The payment page Stripe hosts, where the customer enters their card.
Test card
A fake card number that makes the practice account behave in a chosen way.
Metadata
A note the app attaches to a record so it can recognise it later.
3D Secure
An extra identity check some banks require before a card payment goes through.
